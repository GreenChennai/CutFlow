# ADR-0052: 半成品与成品的边界；剪映降为单向出口

日期: 2026-09-25 · 状态: 已采纳（待落地） · 关联: ADR-0050（抠像降级标注）、ADR-0037（N 后端注册表）、ADR-0044（6.0+ 永不读写）

## 背景

用户明确定义：**「只有最终合成／最终导出才算成品。半成品能够被用户编辑，同时编辑更改的内容可以被 Agent 感知到同时继续接受修改。这部分如果在剪映里比较困难，可以考虑只支持 CutForge。」**

现状：剪映草稿被当成「交付物」之一（README 交付清单里有它），但它其实是**可编辑工程**；而 CutForge 工程**没有在交付面出现**过。结果：用户不知道「哪个是能改的、哪个是最终版」。

## 决策

1. **三分产物**：

| 类 | 定义 | 落点 | 可否回环 |
|---|---|---|---|
| **工程** | S0–S11 全部中间产物 + 母版 | 工程区阶段目录 | ✅（`rebuild.py` + 阶段缓存） |
| **半成品** | 可继续编辑且**编辑可被 Agent 感知**的产物 | 工程区内（**不进 `成品/`**） | ✅ **双向**（CutForge 主通道） |
| **成品** | 最终合成／最终导出 | **`成品/`**（只读语义） | ❌（不需要） |

2. **`成品/` 内容清单**（**只放不可编辑产物**）：

```
成品/
├── 成片/                    成片_<ratio>_<logo>_<profile>.mp4（多画幅 × 多变体）
├── 字幕/                    subtitles.ass / master.srt
├── 封面/                    封面.png（+ 需要时 3:4 / 16:9 各一）
├── 文案/                    metadata.json（标题/简介/Tag）+ 各平台文本
├── 说明书/
│   ├── 交付说明书.md        含降级项、抠像质量判定、版权与 AI 标识、平台适配说明
│   └── 决策说明书.md        每个参数从哪来（--auto 时）
├── 对账.md                  deliverables 清单 + 齐全性判定（缺项则此处红标并非零退出）
└── 半成品入口.md            ★ 指针：说明「可继续编辑的工程在哪」，不复制工程本身
```

3. **半成品落点**（**全在工程区**）：
   - **CutForge 工程** = `05_时间线工程/project.json`（**同源唯一**，不复制副本）；
   - **剪映 5.9 草稿** = `05_时间线工程/导出/剪映59/`（`rs_jy_draft` 产出）；
   - `成品/半成品入口.md` 只写路径与「怎么改 → 怎么让 Agent 接住」的两步说明。
4. **剪映降为单向出口**：保留「IR → 5.9 明文草稿」导出能力（用户可在剪映里精修），但**不再承诺回环**——`rules/jianying-verification.md` 的「诚实验收说明」需增补一节「**为什么不做回环**」（5.9 明文草稿可解析，但剪映内部会对草稿做规范化重排，元素 id 不稳定，无法建立可信的内容寻址锚点；6.0+ 加密，永不读写）。文档中所有「剪映草稿是交付物」的表述改为「剪映草稿是**半成品出口**」。
5. **`成品/` 的生成方式**：`rs_ingest.py deliverables --publish`（新子命令）从工程区**拷贝／衍生**最终产物到 `成品/`，并跑真对账。**拷贝，不是移动**——工程区仍保留母版。
6. **`rs_cleanup` 语义收敛**：工程区可按白名单清理，`成品/` **永不被清理**（只允许 `--publish` 覆写）。

## 取舍

- 付出：多一次拷贝（磁盘占用）；交付物与工程侧母版可能不同步（靠 `--publish` 时间戳与 hash 留痕）。
- 换来：用户一眼知道「哪个能改、哪个是最终版」；`成品/` 可以整个打包发走；工程区可以放心清理。

## 被否决的替代

- **剪映草稿也进 `成品/`**：否决——它是可编辑工程，放进「只读交付区」会造成语义污染（用户已明确其为半成品）。
- **把 CutForge 工程复制一份进 `成品/`**：否决——产生**双份真相源**，回改时无法判断改哪份（违反 ADR-0033「文件为真相源」）。
- **追求剪映双向回环**：否决——技术成本高、不可靠（见第 4 条理由），用户已同意只支持 CutForge。

## 影响

- `rs_ingest.py`（新增 `deliverables --publish`）、`rs_jy_draft.py`（落点改到 `05_时间线工程/导出/剪映59/`）、`rs_cleanup.py`（`成品/` 保护）、`README.md` 交付清单、`rules/archive.md`、`rules/jianying.md`、`rules/jianying-verification.md`。
- 新增 `rules/editing-roundtrip.md`（双向编辑闭环与剪映单向出口的诚实说明）。

## 四问

| 问 | 答 |
|---|---|
| 旧工程 | `成品/` 不存在 → `--publish` 按需创建；旧交付物仍在 `06_成片输出/` 顶层，`--publish` 时自动归集（不改旧结构，只在 publish 时读）。 |
| 门禁 | `tests/test_deliverables.py` 扩展：①`成品/` 内**不得出现** `project.json`／`wordline.json`／`cutlist.json`／`notes.json`／`*.draft_content.json`（只读区断言）；②缺项非零退出 `DELIVERABLES_INCOMPLETE`（保留）；③`--publish` 幂等（重复执行不产生重复文件）；④`rs_cleanup` 不得触碰 `成品/`。 |
| 验收 | 一条工程执行 `--publish` → `成品/` 自洽（`对账.md` 全绿）；把这套 `成品/` 单独拷到另一台机器可正常观看；`成品/半成品入口.md` 指向的工程可被 CutForge 打开。 |
| 回滚 | 删除 `成品/` 不影响工程；`--publish` 覆写前先备份旧 `成品/` 到 `_内部状态/backup/publish-<ts>/`。 |
