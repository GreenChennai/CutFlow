# ADR-0056: 渲染性能——冗余探测合并与同级并行

日期: 2026-09-26 - 状态: 已采纳(v0.20 已落地) - 来源: 《CutFlow-迭代计划-v2-20260925》主册 §3(转写自桌面蓝本,以蓝本为权威)

**状态**：已采纳(v0.20 已落地) · **关联**：v1 §6 性能预算、分册03 性能热点

#### 背景

分册03 核实：**全仓无 `lru_cache`（0 命中）**；同一素材被重复 ffprobe（`rs_render.py:415` 主轨、`:720` overlay、`:616`/`:624` 对同一段各发一次）→ 粗算 **≈3N 次 ffprobe**；**全仓无并行**（`ThreadPool|concurrent|multiprocessing` 0 命中）——段渲染与 `rs_brand` 变体循环都可并行，直接拖累既有的「4 变体 ≤1.5× 单变体」目标（BACKLOG D5）。

#### 决策

1. **探测合并**：`rs_render` 内新增**单次探测**——每段只探测一次，结果缓存（进程内 `lru_cache` + 可选的跨运行 `media_index.json`），供 `probe_clip` / `_video_stream_len` / `_seg_has_audio` 共用。
2. **段级并行**：`step_segment` 的逐段渲染改为**可配置并发**（默认 `min(4, CPU/2)`，`--jobs N` 可调，`--jobs 1` 回到串行）。段间**本就无依赖**（既有设计就是逐段渲染再 concat）。
3. **变体级并行**：`rs_brand` 的变体矩阵改为并发（同样 `--jobs`）。目标是让 BACKLOG D5 的「4 变体 ≤1.5×」**真正达标**。
4. **确定性不受影响**：并行只改**执行顺序**，不改产物内容——`concat` 顺序仍按 IR 的显式顺序；并发度不进入缓存键（否则并发度变化会导致全量失效），但进入 `pipeline.json` 留痕。
5. **`rs_cut` 的 O(n²) 相似度**：候选窗口先按「句数 ≤6 或间隔 ≤30s」剪枝（现有判据）后再两两比，并加**早停**（比例已低于阈值即停）。

#### 取舍

- 付出：并发带来的日志交错、临时文件命名需带段号（避免冲突）。
- 换来：长片与多变体出片时间显著下降；ffprobe 调用从 3N 降到 N。

#### 被否决的替代

- **把并发度写进缓存键**：否决——改并发度会全量重渲，反直觉且浪费。
- **直接上 multiprocessing**：否决——Windows 上进程启动成本高且 ffmpeg 本身已多线程，**线程池足够**（瓶颈在子进程与 IO）。
- **先上 GPU 渲染**：否决——超出本册范围，且与「FFmpeg 为 Golden 基准」冲突。

#### 四问

| 问 | 答 |
|---|---|
| **旧工程怎么办** | `--jobs` 默认自动；产物与串行**字节级一致**（有序 concat），旧工程无感知。 |
| **门禁怎么把守** | ①`tests/test_render_parallel.py`：`--jobs 1` 与 `--jobs 4` 的产物 **hash 一致**；②ffprobe 调用次数断言（用 mock 计数，≤N+常数）；③临时文件命名含段号，跑完无残留。 |
| **怎么验收** | 标准夹具工程：并行 vs 串行的墙钟时间对比（记录进 `docs/context-budget.md` 的性能趋势）；4 变体矩阵 ≤1.5× 单变体（清 BACKLOG D5）。 |
| **怎么回滚** | `--jobs 1` 即回到现行为；探测缓存文件可删（自动重建）。 |
