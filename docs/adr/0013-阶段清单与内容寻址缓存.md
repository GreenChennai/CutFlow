# ADR-0013:阶段清单与内容寻址缓存(增量编排)

状态:已采纳 ｜ 日期:2026-09-10

## 背景

用户反馈「各个阶段不可编辑,比如一个绿幕视频,我想修改背景,那么还得让 Agent 从头到尾跑一遍,小号不少 Token,一跑就是 20 分钟+;或者说字幕我要改一个字 / 调整语句顺序,也要从头到尾跑一遍」。

审计发现:旧 `compose.md` 的「中间件」一节全文是——

> `06_output/_build/<ratio>/` 下 `seg_*/base/composed/mixed/subtitled` 可复用;**改了字幕只重跑 step6-7(重调 rs_render 会全跑,手改时可复用 mixed.mkv)**。

产物摆在目录里,能不能复用、复用哪几个,**靠 Agent 每次现场判断**:没有依赖声明、没有脏值计算、没有工具版本记录,也没有"为什么慢"的可观测性。

## 决策

1. 引入**阶段清单** `05_ir/pipeline.json` + 权威状态 `_state/S*.json`;
2. **缓存键公式**:
   `key = sha1( 上游产物内容 hash + 阶段参数快照 + 本阶段脚本文件 hash + 外部服务版本 )`
   —— 使用**内容 hash 而非 mtime**;脚本文件 hash 必须计入,否则出现「改了代码但缓存命中」的幽灵 bug(增量系统最致命的一类故障);
3. **缓存粒度 = segment**。粗于 segment 没收益,细于 segment 管理成本爆炸;`_state/seg_S3_0007.json` 记录每个 seg 的输入 hash,只重渲 hash 变了的 seg,其余 concat 复用;
4. `params` 记录**当时的参数快照**——旧工程按当时参数可复现(例如竖屏字数从 16 下调到 12 后,旧工程仍按 16 复现,不追改);
5. 命令语义:`--status`(状态灯)/ `--from S3` / `--only S7` / `--dirty` / `--explain S7`(指出**具体哪个输入/脚本**变了)/ `--mark S4`(人工介入后标记);
6. 阶段注册表固定为 **S0–S10**(11 个),阶段边界按「可独立验证」划分,上限 12 个;
7. `status ∈ {done, stale, missing, failed}`,**stale 时绝不静默继续**;
8. 落地点:改写 `compose.md` 的「中间件」一节,从**人肉复用**升级为**声明式缓存**。

## 后果

| 编辑动作 | 改造前 | 改造后 |
|---|---|---|
| 改一个字幕文字 | 全跑 20min+ | **秒级**(只重生成该卡 ASS 事件 + 重叠一次) |
| 改字幕断句 | 全跑 | 局部 DP 窗口(±3 卡) |
| 调整语句顺序 | 全跑 | S2 起重跑,**不重新转写**(S1 命中) |
| 换背景图 | 全跑 | 只重渲受影响 seg |
| 换 BGM | 全跑 | S6 起重跑 |
| 换 Logo / 加变体 | 不支持 | S5 + S10,其余全部命中缓存 |

- 验收线:无改动重跑 `--from S3` 全程命中 ≤2s;单卡改字端到端 ≤10s;
- 新增风险:缓存键漏项会导致"该重跑没重跑",因此 `--explain` 必须能把差异摊开给人看;
- 阶段划分与文件命名耦合,新增阶段需同步更新 `rs_run.spec()` 与 SKILL.md §1 表(已有测试防漂移)。
