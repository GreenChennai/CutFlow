# ADR-0058: 审阅发现的处置纪律（缺陷 → 计划的正规通道）

日期: 2026-09-26 - 状态: 已采纳(v0.20 已落地) - 来源: 《CutFlow-迭代计划-v2-20260925》主册 §3(转写自桌面蓝本,以蓝本为权威)

**状态**：已采纳(v0.20 已落地) · **关联**：v1 ADR-0041（禁止现写脚本）、`docs/BACKLOG.md`

#### 背景

用户要求：「**review 期间如果有其他我没考虑到的内容 / Bug / 优化也能写进迭代计划中**」。本轮 review 已产出 3 个高危契约缺陷、4 处静默吞能力、性能热点与测试盲区（分册03）。

但**「写进计划」不等于「修好」** —— 必须防止发现的问题在文档里烂掉（这正是 v1 §1.8 根因 #2/#3 的教训）。

#### 决策

1. **每个发现必须带五要素**（缺一即视为未登记）：`编号 / 证据（文件+行号）/ 严重度 / 处置（修|不修|登记待办）/ 归属里程碑`。
2. **严重度定义**：
   - **高**：功能静默出错、崩溃、数据/交付错误、合规风险；
   - **中**：契约不一致、性能损失、可维护性风险、静默降级；
   - **低**：体验瑕疵、命名不一致、无实质风险。
3. **高严重度必须在 v2 内修完**（M11）；中严重度至少给出结论（修 / 明确不修 + 理由）；低严重度可登记待办。
4. **「不修」必须写理由**（并给出代价对比），不允许空白。
5. **发现入 `docs/BACKLOG.md`**：分册03 的结论必须逐条落到 BACKLOG（新增条目），文档与台账**双向对拍**（分册05 的门禁）。

#### 取舍

- 付出：每条发现要写五要素，比随口说麻烦。
- 换来：发现不会烂掉；「不修」是显式决策而非遗忘。

#### 被否决的替代

- **只把发现写在分册03 就完事**：否决——文档与台账脱钩，下个 Agent 不会回看。
- **全部塞进 BACKLOG 不分类**：否决——高严重度会被淹没，无法保证本轮修完。

#### 四问

| 问 | 答 |
|---|---|
| **旧工程怎么办** | 缺陷修复可能改变行为（如 `cut/none` 从「报错」变「合法」、`bgm.loop:false` 从「忽略」变「生效」）——**每处行为变更必须在 CHANGELOG 显式喊**。 |
| **门禁怎么把守** | `tests/test_backlog_sync.py`：分册03 的每条 `编号` 在 `BACKLOG.md` 里能找到对应行；反之 BACKLOG 新增的 P0/P1 在分册03 有出处。 |
| **怎么验收** | 高严重度缺陷全修且有回归测试（红→绿）；中严重度 100% 有结论；BACKLOG 对拍门禁绿。 |
| **怎么回滚** | 逐缺陷独立提交，可单条回滚；回滚说明必须写明恢复的旧行为。 |
